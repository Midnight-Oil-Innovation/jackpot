Auth & Identity

When you click Sign in with Google, JACKPOT does not trust Google alone — it runs your email through two more checks before letting you in.

The secure research building metaphor
Think of JACKPOT like a high-security lab building. Google is the government ID office — they confirm you are who you say you are. The domain whitelist is the approved-organisations list at the front desk. Your JWT is the key card you receive after passing both checks. And your role determines which rooms you can enter.
🪪

Authentication

Who are you?

Handled by Google OAuth + domain whitelist + user-exists check.

🔑

Authorization

What can you do?

Handled by roles: Platform Admin, Lab Director, Lab Collaborator, Lab Reader.

Why this matters to you: When a researcher says "I cannot access this lab's data," the fix depends on which check failed. A blocked email domain is a different fix from a missing role — and knowing which is which saves hours of guessing.

The Three-Gate Login Flow

Every login runs through exactly three gates in sequence. Fail any gate and you get a 403 before JACKPOT even checks the next one.

1
Google Exchange

Trade the auth code for the researcher's email address

2
Domain Whitelist

Is the email domain approved? (e.g. asu.edu)

3
User Exists

Has a Platform Admin created an account for this email?

CODE — backend/routers/auth.py 
@router.post("/google/login")
async def google_login(code: str, request: Request, response: Response) -> dict:
    redirect_uri = settings.google_oauth_redirect_url
    user_info = await exchange_google_code(code, redirect_uri)
    email = user_info["email"]

    if not check_domain_whitelist(email):
        raise HTTPException(
            status_code=403,
            detail=f"Domain '{email.split('@')[1]}' is not authorised. "
            "Contact a Platform Admin.",
        )

    user = get_user_by_email(email)
    if not user:
        raise HTTPException(
            status_code=403,
            detail="Account not found. A Platform Admin must create your "
            "account before you can log in.",
        )

    access_token = issue_access_token(user["id"], email)
    refresh_token = issue_refresh_token(user["id"], email)

    response.set_cookie(
        "access", access_token, httponly=True, secure=True, samesite="lax", max_age=900
    )
    response.set_cookie(
        "refresh", refresh_token, httponly=True, secure=True, samesite="lax", max_age=604800
    )

    return {"email": email, "name": user.get("name", "")}
PLAIN ENGLISH

Register this as the POST /google/login endpoint.

Gate 1 — Google exchange: Take the one-time auth code the browser sent and trade it with Google for the researcher's actual email address.

Domain whitelist check: Extract the domain part of the email (everything after the @). If it is not on the approved list, stop here with a 403 error and tell the user to contact a Platform Admin.

Gate 2 — User exists check: Even if the domain is approved, look up whether a Platform Admin has already created an account for this exact email. If not, block with another 403.

Gate 3 passed — mint credentials: Create a short-lived access token (15 min) and a longer-lived refresh token (7 days).

Set cookies: Both tokens are stored as httpOnly cookies, meaning JavaScript can never read them — they are invisible to the browser but automatically sent with every request.

Return success: Send the email and display name back to the frontend to show in the UI. The real credential is already in the cookie.

What is inside a JWT?
The JWT contains a sub (user ID), email, expiry time, and a type field. It is signed with HS256 so any tampering is detectable.
Why 15 minutes for the access token?
Short-lived tokens limit the damage if stolen — they expire before an attacker can do much. The 7-day refresh token handles the silent re-authentication so you do not have to log in every 15 minutes.

Who Can Do What — Roles & Guards

Authentication gets you through the front door. RBAC determines which rooms you can enter once inside.

Platform Admin

Access everything — all labs, all data. Bypasses all lab-level checks.

Lab Director

Full control of their assigned lab — can invite members, manage projects.

Lab Collaborator

Read and write access to their lab. Cannot manage membership.

Lab Reader

Read-only. Cannot upload samples or modify anything.

Bioinformatics User

Access to pipeline runs and analysis tools across their assigned projects.

Data Analyst

Read access to structured data for downstream analysis and reporting.

CODE — backend/auth/guards.py 
def require_platform_admin(current_user: dict) -> None:
    if not current_user.get("is_platform_admin"):
        raise HTTPException(status_code=403, detail="Platform Admin required.")

def require_lab_director(current_user: dict, lab_id: int) -> None:
    if current_user.get("is_platform_admin"):
        return
    m = get_user_lab_membership(current_user["id"], lab_id)
    if not m or not m.get("is_lab_director"):
        raise HTTPException(status_code=403, detail="Lab Director required.")

def require_lab_access(current_user: dict, lab_id: int) -> None:
    if current_user.get("is_platform_admin"):
        return
    if get_user_lab_membership(current_user["id"], lab_id):
        return
    rows = execute_query(
        "SELECT 1 FROM project_membership pm "
        "JOIN projects p ON p.id = pm.project_id "
        "WHERE pm.user_id = :uid AND p.lab_id = :lid LIMIT 1",
        {"uid": current_user["id"], "lid": lab_id},
    )
    if not rows:
        raise HTTPException(status_code=403, detail="Lab access required.")
PLAIN ENGLISH

require_platform_admin: Blunt check — if the user does not have the is_platform_admin flag, immediately refuse with a 403. No exceptions.

require_lab_director — the bypass pattern: The very first line checks is_platform_admin. If true, return immediately — Platform Admins skip every subsequent check. This is the "master key" pattern used throughout all guards.

Lab director check: For everyone else, look up the user's membership row for this specific lab and check the is_lab_director flag.

require_lab_access — three ways in: (1) Platform Admin — instant pass. (2) Direct lab membership — also a pass. (3) Project membership: even if you are not a lab member directly, if you belong to any project inside this lab, you get access too.

Why project membership grants lab access: Collaborators are often added to a specific project, not the whole lab. This SQL query checks whether any project you belong to lives inside the requested lab — so project members are not locked out of lab-level views.

If none of the three checks pass: Raise a 403 Lab access required. The frontend shows this as "you do not have access."

Bonus: The Local Dev Bypass
When settings.env == "local", JACKPOT skips the entire cookie/JWT check and pretends the mock_user_email from your .env file is logged in with Platform Admin rights. This is how you develop locally without needing a real Google account or cookies. It only works in local mode — the check is the very first thing get_current_user does.
