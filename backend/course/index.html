Why does each service get its own port?

Your computer has 65,535 numbered doors (ports). Each service claims one. That way, four programs can all run simultaneously without stepping on each other.

Reading docker-compose.yml

One file tells Docker how to start the entire stack. Here it is alongside plain English.

CODE 

services:

  postgres:
    image: postgres:16
    container_name: jackpot_postgres
    environment:
      POSTGRES_USER:     jackpot
      POSTGRES_PASSWORD: jackpot
      POSTGRES_DB:       jackpot_db
    ports:
      - "5432:5432"
    volumes:
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql

  minio:
    image: minio/minio:latest
    container_name: jackpot_minio
    command: server /data --console-address ":9001"
    ports:
      - "9000:9000"
      - "9001:9001"

  api:
    container_name: jackpot_api
    ports:
      - "8000:8000"
    depends_on:
      postgres:
        condition: service_healthy
    command: /opt/venv/bin/uvicorn backend.main:app
      --host 0.0.0.0 --port 8000 --reload

  ui:
    container_name: jackpot_ui
    ports:
      - "8501:8501"
    depends_on:
      - api
    command: /opt/venv/bin/streamlit run app.py
PLAIN ENGLISH

services: — Here are all the programs that make up JACKPOT. Docker will start each one as its own isolated container.

postgres / image: postgres:16 — Use the official PostgreSQL version 16 database. Docker downloads it automatically if it is not already on your machine.

environment / POSTGRES_USER & PASSWORD & DB — Set startup configuration via environment variables. The database will create a user named “jackpot” with password “jackpot” and a database called “jackpot_db.”

ports: “5432:5432” — Open door 5432 on your laptop and connect it to door 5432 inside the container. Format is your-machine:inside-container.

volumes: ./db/init.sql — When PostgreSQL starts for the first time, run this SQL file to create all the tables. A volume makes a file from your computer visible inside the container.

minio / command: server /data --console-address “:9001” — Start MinIO’s file server and also open its browser-based admin dashboard on port 9001.

api / depends_on: postgres / condition: service_healthy — Do not start the API until PostgreSQL has fully started and passed its health check. No point starting reporters before the wire desk opens.

command: uvicorn backend.main:app --reload — Start the API using uvicorn, a high-performance Python web server. The --reload flag means it restarts automatically when you change code.

ui / depends_on: api — Start Streamlit only after the API is running. The UI has nothing to show until the API is ready to answer its questions.

How the API Knows Everyone Is Home

Before the API accepts any traffic, it checks whether the database is reachable. This is the /health endpoint from backend/main.py.

CODE 

@app.get("/health")
def health() -> dict:
    try:
        execute_query("SELECT 1")
        db_status = "connected"
    except Exception:
        db_status = "unavailable"
    return {
        "status": "ok",
        "version": __version__,
        "project": "JACKPOT",
        "database": db_status
    }
PLAIN ENGLISH

@app.get(“/health”) — Register this function as the handler for GET /health. Any browser or monitoring tool can hit localhost:8000/health to ask “is JACKPOT alive?”

execute_query(“SELECT 1”) — Run the simplest possible database query — just return the number 1. If the database is reachable, this succeeds instantly. If not, it throws an error.

try / except Exception — If the query fails for any reason, catch the error gracefully instead of crashing. Set db_status to “unavailable” so the caller knows what is wrong.

return {...} — Send back a small JSON object with the app version, project name, and database status. Monitoring tools read this to decide whether to send you an alert.

🔧
Practical tip: visit localhost:8000/health

While the stack is running, open that URL in your browser. You will see live JSON showing whether the database is connected. It is the fastest way to confirm all four services started correctly.

How the Stack Knows Its Own Address

The Settings class in backend/config.py is where every service address, secret, and toggle lives. These values come from environment variables so the same code works locally and in production.

CODE 

class Settings(BaseSettings):
    env: str = "local"
    database_url: str = "postgresql://jackpot:jackpot@localhost:5432/jackpot_db"
    storage_endpoint: str | None = None
    storage_bucket_sequences: str = "jackpot-sequences"
    storage_bucket_raw: str = "jackpot-raw"
    storage_bucket_staging: str = "jackpot-staging"
    secret_key: str = "dev-secret-key-change-in-prod"
    scheduler_enabled: bool = True

    class Config:
        env_file = ".env.local"

    def validate_for_production(self) -> None:
        if self.env == "gcp":
            if self.secret_key == "dev-secret-key-change-in-prod":
                raise RuntimeError("SECRET_KEY is still the default dev value.")

@lru_cache
def get_settings() -> Settings:
    return Settings()
PLAIN ENGLISH

class Settings(BaseSettings) — A configuration object that reads its values from environment variables automatically. If a variable is not set, it falls back to the default shown here.

database_url — The full address for connecting to PostgreSQL, including username, password, host, port, and database name. Locally this points to the Docker container.

storage_bucket_sequences / raw / staging — The three MinIO buckets where JACKPOT puts different kinds of genome files.

secret_key — Used to sign login tokens. The default value is intentionally labeled “change-in-prod.” The validate_for_production method throws a hard error if you forget.

class Config / env_file — Load environment variables from a file called .env.local on startup. This file is never committed to git — it holds your local secrets.

@lru_cache / get_settings() — lru_cache means the Settings object is created once and reused forever. No repeated file reads. Efficient and safe.

Anatomy of a Route

Every route follows the same recipe. Here's the GISAID export endpoint — one of the more interesting ones.

CODE — backend/routers/gisaid.py 

@router.post("/export/{lab_id}")
def export_gisaid_csv(
    lab_id: int,
    sample_ids: list[int],
    pathogen: str,
    request: Request,
) -> StreamingResponse:
    """Generate a GISAID-compatible CSV for the specified samples."""
    if not sample_ids:
        raise HTTPException(status_code=400, detail="No sample IDs provided.")
    user = get_current_user(request)
    require_lab_access(user, lab_id)
PLAIN ENGLISH

@router.post("/export/{lab_id}") — This is a POST endpoint. The {lab_id} in curly braces is a path parameter — it gets pulled out of the URL automatically.

lab_id: int — FastAPI sees this matches the URL parameter and fills it in. The colon means "this must be a whole number."

sample_ids: list[int] — These come from the request body — a list of sample IDs the caller wants exported. FastAPI reads the JSON body and validates it automatically.

request: Request — This is dependency injection — FastAPI sees the type hint and automatically passes the incoming request object so we can read headers and the logged-in user.

-> StreamingResponse — The return type. A StreamingResponse streams the CSV file back to the browser instead of loading the whole thing into memory first.

raise HTTPException(400) — If no sample IDs were provided, immediately return an error. The 400 status code means "bad request — you sent invalid input."

require_lab_access — Check that the logged-in user actually has permission to access this lab. If not, this raises a 403 error automatically.

The Middleware Layer: Stamping Every Request

Before any router sees a request, two middleware layers process it. Here's the one that stamps each request with a unique ID.

CODE — backend/middleware.py 

import uuid
from fastapi import Request
from starlette.middleware.base import BaseHTTPMiddleware

class RequestIDMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        request_id = str(uuid.uuid4())
        request.state.request_id = request_id
        response = await call_next(request)
        response.headers["X-Request-ID"] = request_id
        return response
PLAIN ENGLISH

import uuid — Pull in the library for generating universally unique IDs — random identifiers guaranteed to never repeat across the planet.

class RequestIDMiddleware — Define a middleware class. Every incoming HTTP request will run through this code.

async def dispatch — This method runs for every single request, no exceptions. It receives the request before any router touches it.

uuid.uuid4() — Generate a brand new UUID — a random string like a3f2-91bc-7e14-... — unique to this exact request.

request.state.request_id = request_id — Attach the ID to the request object so every handler function and log line downstream can reference it.

await call_next(request) — Pass the (now-stamped) request along to the next layer — the CORS check, then the router. We wait for the full response to come back.

response.headers["X-Request-ID"] — Stamp the same ID onto the response headers. When a user reports a bug, support can look up this exact request ID in the server logs and see every log line from that request.

Auth & Identity

When you click Sign in with Google, JACKPOT does not trust Google alone — it runs your email through two more checks before letting you in.

The secure research building metaphor
Think of JACKPOT like a high-security lab building. Google is the government ID office — they confirm you are who you say you are. The domain whitelist is the approved-organisations list at the front desk. Your JWT is the key card you receive after passing both checks. And your role determines which rooms you can enter.
🪪

Authentication

Who are you?

Handled by Google OAuth + domain whitelist + user-exists check.

🔑

Authorization

What can you do?

Handled by roles: Platform Admin, Lab Director, Lab Collaborator, Lab Reader.

Why this matters to you: When a researcher says "I cannot access this lab's data," the fix depends on which check failed. A blocked email domain is a different fix from a missing role — and knowing which is which saves hours of guessing.

The Three-Gate Login Flow

Every login runs through exactly three gates in sequence. Fail any gate and you get a 403 before JACKPOT even checks the next one.

1
Google Exchange

Trade the auth code for the researcher's email address

2
Domain Whitelist

Is the email domain approved? (e.g. asu.edu)

3
User Exists

Has a Platform Admin created an account for this email?

CODE — backend/routers/auth.py 
@router.post("/google/login")
async def google_login(code: str, request: Request, response: Response) -> dict:
    redirect_uri = settings.google_oauth_redirect_url
    user_info = await exchange_google_code(code, redirect_uri)
    email = user_info["email"]

    if not check_domain_whitelist(email):
        raise HTTPException(
            status_code=403,
            detail=f"Domain '{email.split('@')[1]}' is not authorised. "
            "Contact a Platform Admin.",
        )

    user = get_user_by_email(email)
    if not user:
        raise HTTPException(
            status_code=403,
            detail="Account not found. A Platform Admin must create your "
            "account before you can log in.",
        )

    access_token = issue_access_token(user["id"], email)
    refresh_token = issue_refresh_token(user["id"], email)

    response.set_cookie(
        "access", access_token, httponly=True, secure=True, samesite="lax", max_age=900
    )
    response.set_cookie(
        "refresh", refresh_token, httponly=True, secure=True, samesite="lax", max_age=604800
    )

    return {"email": email, "name": user.get("name", "")}
PLAIN ENGLISH

Register this as the POST /google/login endpoint.

Gate 1 — Google exchange: Take the one-time auth code the browser sent and trade it with Google for the researcher's actual email address.

Domain whitelist check: Extract the domain part of the email (everything after the @). If it is not on the approved list, stop here with a 403 error and tell the user to contact a Platform Admin.

Gate 2 — User exists check: Even if the domain is approved, look up whether a Platform Admin has already created an account for this exact email. If not, block with another 403.

Gate 3 passed — mint credentials: Create a short-lived access token (15 min) and a longer-lived refresh token (7 days).

Set cookies: Both tokens are stored as httpOnly cookies, meaning JavaScript can never read them — they are invisible to the browser but automatically sent with every request.

Return success: Send the email and display name back to the frontend to show in the UI. The real credential is already in the cookie.

What is inside a JWT?
The JWT contains a sub (user ID), email, expiry time, and a type field. It is signed with HS256 so any tampering is detectable.
Why 15 minutes for the access token?
Short-lived tokens limit the damage if stolen — they expire before an attacker can do much. The 7-day refresh token handles the silent re-authentication so you do not have to log in every 15 minutes.

CODE — backend/auth/guards.py 
def require_platform_admin(current_user: dict) -> None:
    if not current_user.get("is_platform_admin"):
        raise HTTPException(status_code=403, detail="Platform Admin required.")

def require_lab_director(current_user: dict, lab_id: int) -> None:
    if current_user.get("is_platform_admin"):
        return
    m = get_user_lab_membership(current_user["id"], lab_id)
    if not m or not m.get("is_lab_director"):
        raise HTTPException(status_code=403, detail="Lab Director required.")

def require_lab_access(current_user: dict, lab_id: int) -> None:
    if current_user.get("is_platform_admin"):
        return
    if get_user_lab_membership(current_user["id"], lab_id):
        return
    rows = execute_query(
        "SELECT 1 FROM project_membership pm "
        "JOIN projects p ON p.id = pm.project_id "
        "WHERE pm.user_id = :uid AND p.lab_id = :lid LIMIT 1",
        {"uid": current_user["id"], "lid": lab_id},
    )
    if not rows:
        raise HTTPException(status_code=403, detail="Lab access required.")
PLAIN ENGLISH

require_platform_admin: Blunt check — if the user does not have the is_platform_admin flag, immediately refuse with a 403. No exceptions.

require_lab_director — the bypass pattern: The very first line checks is_platform_admin. If true, return immediately — Platform Admins skip every subsequent check. This is the "master key" pattern used throughout all guards.

Lab director check: For everyone else, look up the user's membership row for this specific lab and check the is_lab_director flag.

require_lab_access — three ways in: (1) Platform Admin — instant pass. (2) Direct lab membership — also a pass. (3) Project membership: even if you are not a lab member directly, if you belong to any project inside this lab, you get access too.

Why project membership grants lab access: Collaborators are often added to a specific project, not the whole lab. This SQL query checks whether any project you belong to lives inside the requested lab — so project members are not locked out of lab-level views.

If none of the three checks pass: Raise a 403 Lab access required. The frontend shows this as "you do not have access."

The Ingest Engine

A researcher uploads a spreadsheet from their lab. That spreadsheet might call the same field "Sample ID" or "Specimen No." or just "ID" depending on which lab made it. How does JACKPOT understand all of them?

The Airport Baggage Metaphor
Your bag goes through X-ray (the harmonizer translates labels), then security check (the validator enforces rules), then customs declaration (the quality tier is assigned), and finally gets a baggage tag with a tracking number (a JACKPOT URI is minted) before reaching the carousel (the database).
🔤

Harmonizer

Translates lab-specific column names into JACKPOT schema field names. Drops empty values silently. Warns on unknowns.

✅

Validator

Checks required fields, valid enums, and date formats. Errors block ingest; warnings pass through.

📅

Epiweek Engine

Computes MMWR epiweek and ISO week from date_collected. Returns nulls when precision is too coarse.

🏷️

URI Minter

Assigns a permanent JACKPOT identifier to every accepted record — the baggage tag that follows the sample forever.

Why should I care? When a batch upload fails, the error message names one of these steps. Knowing "harmonizer warning" vs. "validator error" vs. "quality tier PRELIMINARY" tells you exactly what to fix — and which part of the codebase to ask an AI about.

How the Harmonizer Translates a Row

The core of the harmonizer is a single function. It loops over every key-value pair in a raw CSV row and renames keys according to a mapping file — like a bilingual dictionary. 

def harmonize_row(raw: dict[str, Any], mapping: dict) -> dict[str, Any]:
    column_map: dict[str, str] = mapping.get("column_mappings", {})
    result: dict[str, Any] = {}

    for raw_key, value in raw.items():
        if value is None or (isinstance(value, str) and not value.strip()):
            continue
        schema_key = column_map.get(raw_key, raw_key)
        result[schema_key] = value.strip() if isinstance(value, str) else value

    return result
  1. Function signature — Takes the raw row (a dict of whatever column names the lab used) and the loaded mapping file (which contains the translation dictionary).
  2. Extract the column map — Pulls the "column_mappings" sub-dict from the mapping file. Example entry: "Specimen No." → "sample_id". If the mapping file is empty, defaults to an empty dict (pass-through mode).
  3. Skip blank values — If a cell is None or a blank string, the row is silently skipped with continue. This is why an empty "FASTQ location" cell does not cause a missing-field error — it simply never enters the result dict.
  4. Translate the key — column_map.get(raw_key, raw_key) tries to find a translation. If "Specimen No." is in the map, it becomes "sample_id". If the key is not in the map, it passes through unchanged.
  5. Trim whitespace — String values are stripped of leading and trailing spaces. Non-string values (numbers, dates) are stored as-is.
What about harmonize_csv? The outer function harmonize_csv loops over all rows and calls harmonize_row on each. It also scans the first row for columns not in the mapping and appends a warning string if any are found — that warning does not block ingest, it just tells you the mapping file might be incomplete.
Key insight: The harmonizer is pure translation — it never decides whether a value is valid. That job belongs to the validator. Keeping these concerns separate means you can test each independently.

How Quality Tiers Are Decided

After validation, every accepted record receives one of three quality labels. The decision tree is a simple waterfall — each tier requires everything the tier below it requires, plus more. 

def compute_quality_status(data: dict, validation_result: ValidationResult) -> str:
    if not validation_result.valid:
        return "PRELIMINARY"

    tier3_fields = [
        "originating_lab", "submitting_lab",
        "collection_location_state", "collection_location_county",
        "host_age", "host_sex",
    ]
    if all(data.get(f) for f in tier3_fields):
        return "SUBMITTABLE"

    tier2_fields = ["collection_location_state"]
    precision = data.get("date_collected_precision", "day")
    if precision != "year" and all(data.get(f) for f in tier2_fields):
        return "ANALYZABLE"

    return "PRELIMINARY"
  1. PRELIMINARY (automatic) — If the validator found any errors, the record is immediately labelled PRELIMINARY. It is stored, but flagged as incomplete. No further tier checks run.
  2. SUBMITTABLE (tier 3) — Checked first among passing records. Requires all six fields: both lab names, state and county, plus host age and sex. If every field is present, the record is SUBMITTABLE — ready for external submission (e.g. GISAID).
  3. ANALYZABLE (tier 2) — Requires state-level location and date precision of at least "month" (not just "year"). ANALYZABLE records appear in time-series charts and geographic maps on the dashboard.
  4. PRELIMINARY (fallback) — If neither tier 3 nor tier 2 requirements are met, the record falls back to PRELIMINARY. It is stored and accessible, but excluded from aggregate analyses.
🔴

PRELIMINARY

Invalid record, or missing state location, or date precision is "year" only. Stored but excluded from analysis.

🟡

ANALYZABLE

Has state location and day/month-precision date. Appears in dashboard charts and maps.

🟢

SUBMITTABLE

Has all 6 tier-3 fields: both lab names, state + county, host age + sex. Ready for external submission.

The Data Layer

When a sample is validated and accepted, it needs to be stored in two completely different places — its metadata goes into a database, and its genome files go into object storage. Why two systems instead of one?

🏥

The hospital records metaphor

Think of a hospital records department. Patient charts live in filing cabinets (PostgreSQL) — structured rows with dates, diagnoses, and names that staff can search and cross-reference in seconds. X-ray films and MRI scans live in a separate archive room (object storage) — large files that need cheap bulk storage, not fast lookups. The two rooms exist because they solve fundamentally different problems.

JACKPOT works exactly the same way: PostgreSQL holds every piece of structured metadata (who submitted it, which lab, what status), and MinIO / Google Cloud Storage holds the raw FASTQ and FASTA genome files that can be gigabytes each.

🗄️

PostgreSQL

Structured metadata

Sample records, user accounts, lab memberships, audit logs. Great at searching, filtering, and joining rows. Fast for small structured records.

🪣

Object Storage

Large genome files

FASTQ, FASTA, and submission package files. Cheap per gigabyte, scales to petabytes, accessed by key rather than SQL query.

⚠

Why this matters when debugging

When a genome file is “not showing up in the dashboard,” the problem could live in either place: the metadata row might be missing from PostgreSQL, or the actual file might be in the wrong bucket. Two different systems means two different places to look — knowing which is which cuts debugging time in half.

How JACKPOT Talks to PostgreSQL

Every database call in JACKPOT flows through the same context manager: get_db(). Understanding this one function explains how every query in the system gets a connection, commits work, handles errors, and cleans up.

CODE — backend/database.py (lines 36–56) 
@contextmanager
def get_db():
    _, session_local = _get_engine()
    db: Session = session_local()
    try:
        yield db
        db.commit()
    except Exception:
        db.rollback()
        raise
    finally:
        db.close()


def execute_query(query: str, params: dict | None = None) -> list[dict]:
    with get_db() as db:
        result = db.execute(text(query), params or {})
        if result.returns_rows:
            cols = result.keys()
            return [dict(zip(cols, row, strict=False)) for row in result.fetchall()]
        return []
PLAIN ENGLISH
  1. @contextmanager — This decorator turns the function into a context manager usable with with get_db() as db:. It also enables connection pooling: connections are borrowed from a pool and returned, not opened fresh every time.
  2. session_local() — Borrows one connection from the SQLAlchemy pool and wraps it in a Session object that tracks pending changes.
  3. yield db — Hands the connection to the caller. All the caller’s code runs here. The function is “paused” at this line until the with block exits.
  4. db.commit() — If the caller’s code completed without raising an exception, all changes made in this transaction are committed permanently to the database.
  5. except / db.rollback() — If anything raises an exception, rollback undoes every change made so far in this transaction. The exception is then re-raised so the caller still sees the error.
  6. finally: db.close() — This block always runs, whether the code succeeded or failed. The connection is returned to the pool so the next request can reuse it. Without this, connections would leak.
  7. execute_query — A convenience wrapper. It opens a connection via get_db(), runs the SQL, and converts each result row into a plain Python dict so callers never touch raw database cursor objects.
ⓘ
ACID guarantee — The try/yield/except/finally pattern enforces ACID behaviour. Either the entire batch of work commits, or none of it does. Partial writes that leave the database in an inconsistent state are not possible through this path.

The Audit Log — An Immutable Paper Trail

Every time a sample is created, updated, or deleted, JACKPOT writes a record to the audit_log table. This is not optional — it is a CLIA compliance requirement. The log_audit function is designed so that a logging failure can never roll back the main operation that triggered it.

CODE — backend/audit.py (lines 53–89) 
def log_audit(
    action: str,
    actor_id: int | None,
    resource_type: str,
    resource_id: str,
    before: dict | None,
    after: dict | None,
    metadata: dict | None,
    db_conn,
) -> None:
    """Write immutable audit record. Failures are logged, never raised."""
    try:
        execute_write(
            """
            INSERT INTO audit_log
                (action, actor_id, resource_type, resource_id,
                 before_state, after_state, metadata)
            VALUES
                (:action, :actor_id, :resource_type, :resource_id,
                 :before::jsonb, :after::jsonb, :metadata::jsonb)
            """,
            ...,
        )
    except Exception as exc:
        logger.error("Audit log write failed", exc_info=exc, ...)
PLAIN ENGLISH
  1. What is an audit log? — A record of every meaningful action taken on data: who did it, what resource was affected, what it looked like before, and what it looks like after. Think of it as a security camera that cannot be turned off.
  2. before / after dicts — The snapshot of the record before the change and after it. A compliance auditor can replay exactly what happened to any sample at any point in time.
  3. ::jsonb casts — PostgreSQL stores before/after states as JSONB, a compressed binary format. This makes querying audit history with SQL fast and efficient, even for complex nested state objects.
  4. try / except — failures are swallowed — If the audit INSERT fails (network blip, disk full), the exception is caught and logged to the application log, but it is never re-raised. This is deliberate: an audit notification failure must never roll back a sample write. The sample data is more important than the notification.
  5. Append-only by convention — CLIA regulations require that audit records cannot be altered or deleted. The table has no UPDATE or DELETE paths in the codebase — rows are only ever INSERTed. This is enforced by policy, not a database constraint, which is why the comment in init.sql reads: “CLIA-aware — append-only; never UPDATE or DELETE rows here.”
ⓘ
The audit_log table uses BIGSERIAL for its primary key — a 64-bit auto-incrementing integer. A regular 32-bit serial tops out at ~2 billion rows. A busy genomics platform writing audit records for every sample operation can exhaust that quickly. BIGSERIAL holds over 9 quintillion rows.

The Prop Master: File Detector

Labs name their FASTQ files inconsistently. One lab writes sample_R1.fastq.gz; another writes sample_forward.fastq.gz; another writes sample_L001_R1_001.fastq.gz. The file detector handles all of them with four regex patterns and a normalization map. 

# backend/file_detector.py — lines 46-68

PAIRED_PATTERNS: list[re.Pattern] = [
    re.compile(
        rf"^(?P<prefix>.+?)_(?P<lane>L\d+)_(?P<dir>R[12])(?:_\d+)?{FASTQ_EXT}$",
        re.IGNORECASE
    ),
    re.compile(rf"^(?P<prefix>.+?)_(?P<dir>R[12])(?:_\d+)?{FASTQ_EXT}$"),
    re.compile(rf"^(?P<prefix>.+?)_(?P<dir>[12]){FASTQ_EXT}$"),
    re.compile(rf"^(?P<prefix>.+?)_(?P<dir>forward|reverse){FASTQ_EXT}$",
               re.IGNORECASE),
]

DIRECTION_MAP: dict[str, str] = {
    "r1": "R1", "1": "R1", "forward": "R1",
    "r2": "R2", "2": "R2", "reverse": "R2",
}
  1. Pattern 1 — Lane-based naming Matches filenames like sample_L001_R1_001.fastq.gz. The (?P<lane>L\d+) group captures the lane number. This is the most common Illumina convention for multi-lane runs.
  2. Pattern 2 — Simple R1/R2 Matches sample_R1.fastq.gz or sample_R2_001.fastq.gz. No lane group — just prefix, direction, optional trailing number, and extension.
  3. Pattern 3 — Numeric direction Matches sample_1.fastq.gz or sample_2.fastq.gz. Some older tools drop the R prefix entirely.
  4. Pattern 4 — Word-based direction Matches sample_forward.fastq.gz and sample_reverse.fastq.gz. Case-insensitive so Forward and FORWARD also match.
  5. DIRECTION_MAP normalizes everything After any pattern matches, the captured dir group (which could be "r1", "1", "forward", etc.) is passed through DIRECTION_MAP to become a canonical R1/R2 string. This is why all four conventions produce the same output.
If none of the four patterns match, the file is treated as unpaired. It is not silently discarded — it is recorded as a standalone file. The detector only pairs files it can confidently identify; everything else is kept but not linked.

Notifications and Background Jobs

Two systems run outside the normal request-response cycle: a fire-and-forget notification writer and an hourly scheduler that handles the work no researcher is waiting for. 

# backend/notifications.py — lines 37-77

def create_notification(
    recipient_id: int,
    event_type: str,
    title: str,
    body: str,
    resource_type: str,
    resource_id: str,
    action_url: str | None,
    db_conn,
) -> None:
    """
    Write a notification record synchronously within the
    caller's transaction. Failures are logged and swallowed —
    a notification failure must never roll back the triggering
    action.
    """
    try:
        execute_write(
            "INSERT INTO notifications ...",
            {...},
        )
    except Exception as exc:
        logger.error("Notification write failed",
                     exc_info=exc, ...)
  1. Synchronous — not async The function is a plain def, not async def. It runs inside the caller's database connection and transaction. If a pipeline completion is being committed, the notification INSERT happens in that same commit.
  2. Why swallow exceptions? The try/except catches every possible failure — network blip, constraint violation, full disk. The exception is logged so engineers can investigate, but it is never re-raised. This is the fire-and-forget contract: the notification is best-effort, not guaranteed.
  3. The triggering action always wins If the notification write fails, the sample ingest, pipeline record, or access approval still succeeds. The researcher loses a bell icon — not their data.
  4. When is it called? Any router or background job that completes a meaningful action calls create_notification: pipeline finishes, access request approved, Globus files arrive, scrub override auto-denied.
Background jobs wiring — lifespan context manager The scheduler is started once when FastAPI boots and stopped when it shuts down. Two jobs run every hour: scrub_override_auto_deny and access_request_auto_approve. The scheduler only starts if scheduler_enabled is true in settings — so it is off in unit tests and can be disabled in staging.
Both background job functions are stubs today. They log "not yet implemented" and return. The scheduler wiring, the job IDs, and the docstrings that describe the intended behavior are all in place — only the database queries are pending. When debugging "auto-approve is not working," start by checking whether the scheduler started (scheduler_enabled in settings) before looking at the job logic.

The Press Kit: NCBI Export

When a batch of samples needs to go to NCBI, the portal fields have different names than the BioSample attributes NCBI expects. The TOSTADAS export script does the translation — without modifying the source record. 

# scripts/portal_to_tostadas.py — lines 18-68

BIOSAMPLE_FIELD_MAP: dict[str, str] = {
    "organism_name":              "organism",
    "date_collected":             "collection_date",
    "collection_location_country": "geo_loc_name",
    "host_species":               "host",
    "host_age":                   "host_age",
    "sequencing_platform":        "sequencing_platform",
    "pango_lineage":              "lineage",
}

def convert_sample(sample: dict) -> dict:
    biosample: dict = {}
    for portal_field, ncbi_attr in BIOSAMPLE_FIELD_MAP.items():
        val = sample.get(portal_field)
        if val:
            biosample[ncbi_attr] = str(val)
    country = sample.get("collection_location_country", "")
    state   = sample.get("collection_location_state", "")
    biosample["geo_loc_name"] = f"{country}: {state}" if state else country
    biosample["package"] = SOURCE_TYPE_PACKAGE.get(
        sample.get("source_type", ""), "Generic.1.0"
    )
    return {
        "sample_name":    sample["sample_id"],
        "bioproject":     sample.get("bioproject_accession", ""),
        "biosample_attrs": biosample,
        "fastq_r1":       sample["fastq_r1_uri"],
    }
  1. BIOSAMPLE_FIELD_MAP is the dictionary Each entry maps a JACKPOT portal field name (left) to its NCBI BioSample attribute name (right). "organism_name" becomes "organism"; "date_collected" becomes "collection_date". The source record is never touched.
  2. convert_sample loops the map For each portal field in the map, it reads the value from the sample dict. If a value is present, it is written to the biosample dict under the NCBI attribute name, cast to a string.
  3. Location gets special treatment NCBI expects geo_loc_name in "Country: State" format. The script assembles this from two separate portal fields after the main loop runs.
  4. Package is looked up from source_type NCBI BioSample submissions require a package identifier (e.g. SARS-CoV-2.cl.1.0). SOURCE_TYPE_PACKAGE maps JACKPOT source types to the correct package; unknown types fall back to "Generic.1.0".
  5. Output is a TOSTADAS row, not a JACKPOT record The returned dict has the shape TOSTADAS expects: sample_name, bioproject, biosample_attrs, fastq_r1. This is handed directly to the TOSTADAS submission pipeline.
