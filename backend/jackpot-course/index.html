The Pathogen Detective

What JACKPOT does — and the 8-step journey every pathogen sample takes

A Platform for Tracking Pathogens at the Source

Imagine a disease outbreak is spreading across the host jurisdiction. Health labs are collecting samples — nasal swabs, wastewater, livestock tissue — and sequencing the pathogen's genome to understand how it mutates and spreads.

The problem: every lab uses different file formats, different naming conventions, and different quality standards. Sharing data with global databases like GISAID or NCBI requires strict metadata standards. And every raw sequencing file contains traces of human DNA that must be scrubbed before any sharing.

🧬

Ingest Raw Data

Accept FASTQ and FASTA files plus structured metadata from public health labs.

✅

Validate Quality

Check metadata against a 3-tier quality standard — PRELIMINARY, ANALYZABLE, SUBMITTABLE — so only good data reaches global databases.

🔒

Scrub Human DNA

Remove human genetic material from every sample before it leaves the lab — a legal and ethical requirement for patient privacy.

🌍

Export to Global DBs

Generate GISAID-compatible CSVs and NCBI submission packages so local data feeds global outbreak surveillance in real time.

What Happens When a Lab Uploads a Sample

Imagine a lab technician at a public health laboratory uploads a FASTQ file and fills out a metadata form. Here is every step JACKPOT takes in the next few seconds — in order.

1
File arrives at the API

The file and metadata hit one of 21 router endpoints on the FastAPI server.

2
Authentication check

Guards verify the user's JWT token and confirm they have permission to upload to the requested lab.

3
File type sniffed and paired

The file detector reads the first bytes to confirm the file is genuinely FASTQ (not mislabeled), then pairs R1 and R2 reads together.

4
PII scan

The DLP scanner checks all free-text fields for accidentally included personal information.

5
Metadata validated

The validator checks which quality tier the sample reaches — does it have enough fields to be just stored, analyzed, or submitted to global databases?

6
File staged to cloud storage

The raw file is uploaded to a staging bucket in MinIO (local) or GCS (production).

7
Record written to PostgreSQL

The sample row and an audit log entry are written to the database in the same transaction.

8
Scrubber job queued

A background job is scheduled to remove human DNA from the file. Until scrubbing completes, the sample's scrub_status stays PENDING.

The key insight: one request, many actors

A single upload triggers six different systems in sequence. If any step fails — bad metadata, missing permissions, storage error — the whole request is rejected cleanly and the database stays untouched. This is the beauty of ordered validation.

The Cast

Meet the 21 routers, one database, and the storage layer that holds it all together

Five Layers, One Platform

Think of JACKPOT like a hospital. The FastAPI server is the front desk. The routers are the individual departments. The database is the records room. Storage is the physical file archive.

⚡
FastAPI (main.py)

The entry point. Registers all 21 routers, wires up the CORS policy, starts the background scheduler, and serves the /health endpoint.

🗂️
21 Routers (backend/routers/)

Each router owns a domain: auth, ingest, samples, gisaid, users, organizations, and 15 more. Fully implemented: auth and gisaid. The rest are stubs returning {"status":"not implemented"}.

🗄️
PostgreSQL + SQLAlchemy (backend/database.py)

All 27 tables live here. SQLAlchemy manages the connection pool. Every query goes through execute_query() or execute_write() — routers never touch the database driver directly.

📦
MinIO / GCS (backend/storage.py)

Sequencing files are too large for a database. They live in an S3-compatible bucket. Locally that is MinIO (in Docker); in production it is Google Cloud Storage.

⏰
APScheduler / Cloud Scheduler (backend/jobs.py)

Background jobs run on a schedule: the scrubber queue every 60 seconds, and access-request expiry every night at 2 AM. Locally this uses APScheduler; in production it uses Google Cloud Scheduler.

The Database Helper That Powers Every Write

Every INSERT, UPDATE, and DELETE in JACKPOT goes through execute_write(). Here is the key part of it — with one pattern you will see everywhere.

CODE — backend/database.py 

def execute_write(
    query: str,
    params: dict | None = None,
    conn=None,
) -> list[dict]:
    if conn is not None:
        result = conn.execute(text(query), params or {})
        if result.returns_rows:
            cols = result.keys()
            return [dict(zip(cols, row)) for row in result.fetchall()]
        return []
PLAIN ENGLISH

Define a function that writes to the database. It takes a SQL string, optional parameters, and an optional database connection.

The SQL query to run — written as a plain string like "INSERT INTO orgs ..."

Values to substitute safely into the query — prevents SQL injection attacks.

An existing database session to join, so multiple writes share one transaction.

If a connection was passed in, use it (we are inside a bigger transaction)...

...run the query using that connection.

If the query returned rows (e.g., INSERT ... RETURNING *)...

...get the column names, then zip each row into a dictionary and return them all.

If nothing was returned (e.g., a DELETE with no RETURNING), return an empty list.

💡
RETURNING * — never SELECT after write

PostgreSQL lets you add RETURNING * to an INSERT or UPDATE to get the saved row back immediately. JACKPOT uses this everywhere instead of running a separate SELECT query. One round-trip instead of two — and you always get the database-generated values like auto-increment IDs and timestamps.

Why HTTP-only cookies, not localStorage?

JACKPOT sets JWT tokens as HttpOnly cookies, not in browser localStorage. This means JavaScript on the page cannot access the tokens — a stolen script cannot steal your session. The browser sends them automatically on every request.

How Every Request Gets Verified

Every protected endpoint calls get_current_user() first. Here is the real code from guards.py:

CODE — backend/auth/guards.py 

def get_current_user(request: Request) -> dict:
    settings = get_settings()
    if settings.env == "local":
        rows = execute_query(
            "SELECT * FROM users WHERE email = :e",
            {"e": settings.mock_user_email},
        )
        return rows[0] if rows else {"id": 1, ...}
    token = request.cookies.get("access")
    if not token:
        raise HTTPException(status_code=401, detail="Not authenticated.")
    payload = jwt.decode(token, settings.secret_key, ...)
    rows = execute_query("SELECT ... FROM users WHERE id = :uid", ...)
    return rows[0]

Load the app settings (database URL, secret key, etc.) from environment variables.

If we are running locally (not in production)...

...look up the mock user defined in docker-compose.yml by their email address...

(using a safe parameterized query so nobody can inject SQL)

...and return them as the logged-in user. This lets developers work without real Google login.

In production: read the “access” cookie from the request.

403 vs 401 — two very different errors

401 Unauthorized means “I don't know who you are — please log in.” 403 Forbidden means “I know exactly who you are, and you are not allowed to do this.” When you see a 403 in JACKPOT, look for a missing require_* guard call or an incorrect role assignment.

The Quality Engine

The 3-tier validator, the file detective, and the privacy scrubber that protect every sample

Not All Data Is Created Equal

Think of JACKPOT's quality system like passport control at an airport. Every traveler gets through security (Tier 1). Only those with the right visas can board international flights (Tier 3). Getting through is not binary — it is a spectrum.

The key insight: missing fields do not block ingest. A sample with incomplete metadata is still stored — it just cannot be used for certain purposes. The validator tells you exactly what you need to add to unlock each tier.

🟢

Tier 1 — PRELIMINARY

The minimum to identify who, what, where, and when. sample_id, organism_name, source_type, date_collected, and 3 more required fields. Pipelines can launch immediately.

🟡

Tier 2 — ANALYZABLE

Adds epidemiological context: which lab sequenced it, the preparation method, the sequenced date. Required for epiweek calculations, time-series analysis, and external database indexing.

🔵

Tier 3 — SUBMITTABLE

Adds the fields GISAID and NCBI require: sequencing protocol, originating lab, submitting lab, county. Unlocks GISAID CSV export and NCBI BioSample/SRA submission.

🔬
A sample can be SUBMITTABLE but not ANALYZABLE

If a sample has all Tier 3 fields but only a year-precision date (YYYY, no month), it skips Tier 2 and jumps to Tier 3. NCBI and GISAID accept year-only dates; epiweeks require day and month precision. Both pathways are deliberately supported.

Inside the Validator

The validator checks metadata in a specific order — base fields first, then source-type-specific fields, then tier 2, then tier 3. Here is the structure from the real code:

CODE — backend/validator.py 

BASE_REQUIRED = [
    "sample_id",
    "organism_name",
    "source_type",
    "date_collected",
    "collection_location_country",
    "sequencing_platform",
    "type_of_experiment",
]

SOURCE_REQUIRED: dict[str, list] = {
    "Human": ["external_case_id", "biospecimen_type", ...],
    "Wastewater": ["population_served", "sample_type", ...],
    "Wildlife": ["host_species", "biospecimen_type", ...],
    "Isolate": [],  # no extra fields needed
}
PLAIN ENGLISH

BASE_REQUIRED: these 7 fields must be present on every sample, regardless of type. Missing any one = hard error, ingest rejected.

sample_id — the lab-assigned identifier for this sample

organism_name — which pathogen (e.g., “SARS-CoV-2”)

source_type — where was this collected: Human, Wastewater, Wildlife, etc.

date_collected — when the sample was taken from its source

...plus country, sequencing platform, and experiment type.

SOURCE_REQUIRED: each source type has additional required fields on top of the base 7.

Human samples require an external case identifier (external_case_id) and specimen type.

Wastewater requires flow rate, population served, and sampling method.

Wildlife requires the host species and specimen type.

Isolate has no extra requirements — it is the simplest source type.

A sequencing file called sample.fastq is not automatically a FASTQ file. Someone might have renamed it by accident. JACKPOT's file_detector.py reads the actual bytes inside the file to confirm — and then pairs up R1 and R2 reads automatically.

⚠️
FASTA files skip scrubbing automatically

If a sample has only FASTA files (no raw FASTQ reads), the human-read scrubbing step is automatically skipped — scrub_status = SKIPPED. FASTA files are assembled sequences with human reads already removed by the sequencer. Only the validator (not the router) is allowed to set this status.

The Safety Net

Immutable audit trails, background jobs, and how to debug JACKPOT when something goes wrong

The Logbook That Cannot Be Erased

Imagine a ship's logbook — every entry is written in ink, dated and signed, and kept permanently. You can add new entries but you can never erase old ones. That is JACKPOT's audit log.

Every state-changing action — creating a sample, changing a permission, approving a scrub request — writes an immutable record to the audit_log table. Public health platforms are legally required to prove who changed what and when.

action What happened: CREATE_SAMPLE, UPDATE_ORG, ADD_LAB_MEMBER, APPROVE_SCRUB_SKIP...
actor_id Who did it — the user ID of the person who triggered the change
resource_type + resource_id What was affected — e.g., resource_type=“sample”, resource_id=“42”
before_state / after_state The full JSON snapshot of the record before and after the change — like git diff for data
metadata Any extra context — IP address, request ID, pipeline run ID, etc.
💡
Audit failures never crash the request

log_audit() is wrapped in a try/except. If the audit write fails, the error is logged to the application logger but not raised — the main operation still succeeds. The philosophy: a broken audit log is a serious alert, but it should not prevent a lab from uploading a sample during a disease outbreak.

The Audit Log Write — In Code

Here is the entire log_audit() function from backend/audit.py. Notice the JSONB casting and the silent-failure design:

CODE — backend/audit.py 

def log_audit(action, actor_id, resource_type,
             resource_id, before, after, metadata,
             db_conn) -> None:
    try:
        execute_write(
            """INSERT INTO audit_log
               (action, actor_id, resource_type,
                resource_id, before_state, after_state,
                metadata)
               VALUES (:action, :actor_id, :resource_type,
                :resource_id, :before::jsonb,
                :after::jsonb, :metadata::jsonb)""",
            {"action": action, ...},
            conn=db_conn,
        )
    except Exception as exc:
        logger.error("Audit log write failed", exc_info=exc)
PLAIN ENGLISH

Define log_audit. It takes the action, who did it, what resource was affected, before/after snapshots, and an open database connection.

Returns None — this function does not give anything back; it just writes to the DB.

Try to run the INSERT. If anything goes wrong, jump to “except”.

Execute a write using the same database connection that the parent operation is using.

Insert a row into the audit_log table with all the provided fields.

The ::jsonb cast tells PostgreSQL to store the dict as binary JSON — queryable and indexed.

conn=db_conn means this INSERT shares the same transaction as the parent operation. Commit or rollback together.

If the INSERT fails for any reason (constraint, disk full, etc.)...

...log the error to the application logs but do NOT raise it. The caller's code keeps running.

The Night Crew — Background Jobs

Some work is too slow to do during a user's request — like removing human DNA from a 5 GB sequencing file. JACKPOT runs these as scheduled background jobs, separate from the main API.

⏱️

Scrubber Queue

Runs every 60 seconds. Finds all samples with scrub_status = PENDING and submits them to the human-read removal pipeline. Updates status to IN_PROGRESS, then COMPLETE or FAILED.

🌙

Access Request Expiry

Runs every night at 2:00 AM. Finds pending dataset access requests that have exceeded their approval window and auto-denies them. Writes DENY_ACCESS_REQUEST to the audit log.

P

🧠
Why not Celery or Redis?

Many apps use Celery for background work. JACKPOT does not — it is explicitly listed in the architecture constraints as “no Celery, no Redis as task broker.” Simpler infrastructure for a platform that needs to be operated by public health agencies, not dedicated DevOps teams.

⚠️
The single most common JACKPOT bug: wrong is_active column name

Organizations and Labs use active (no prefix). Everything else uses is_active. Mixing these up causes silent SQL errors where a soft-delete does not take effect or an active filter returns wrong results. Always check the schema when writing queries against orgs or labs.
