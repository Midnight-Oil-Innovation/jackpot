The Safety Net

Immutable audit trails, background jobs, and how to debug JACKPOT when something goes wrong

The Logbook That Cannot Be Erased

Imagine a ship's logbook — every entry is written in ink, dated and signed, and kept permanently. You can add new entries but you can never erase old ones. That is JACKPOT's audit log.

Every state-changing action — creating a sample, changing a permission, approving a scrub request — writes an immutable record to the audit_log table. Public health platforms are legally required to prove who changed what and when.

action What happened: CREATE_SAMPLE, UPDATE_ORG, ADD_LAB_MEMBER, APPROVE_SCRUB_SKIP...
actor_id Who did it — the user ID of the person who triggered the change
resource_type + resource_id What was affected — e.g., resource_type=“sample”, resource_id=“42”
before_state / after_state The full JSON snapshot of the record before and after the change — like git diff for data
metadata Any extra context — IP address, request ID, pipeline run ID, etc.
💡
Audit failures never crash the request

log_audit() is wrapped in a try/except. If the audit write fails, the error is logged to the application logger but not raised — the main operation still succeeds. The philosophy: a broken audit log is a serious alert, but it should not prevent a lab from uploading a sample during a disease outbreak.

The Audit Log Write — In Code

Here is the entire log_audit() function from backend/audit.py. Notice the JSONB casting and the silent-failure design:

CODE — backend/audit.py 

def log_audit(action, actor_id, resource_type,
             resource_id, before, after, metadata,
             db_conn) -> None:
    try:
        execute_write(
            """INSERT INTO audit_log
               (action, actor_id, resource_type,
                resource_id, before_state, after_state,
                metadata)
               VALUES (:action, :actor_id, :resource_type,
                :resource_id, :before::jsonb,
                :after::jsonb, :metadata::jsonb)""",
            {"action": action, ...},
            conn=db_conn,
        )
    except Exception as exc:
        logger.error("Audit log write failed", exc_info=exc)
PLAIN ENGLISH

Define log_audit. It takes the action, who did it, what resource was affected, before/after snapshots, and an open database connection.

Returns None — this function does not give anything back; it just writes to the DB.

Try to run the INSERT. If anything goes wrong, jump to “except”.

Execute a write using the same database connection that the parent operation is using.

Insert a row into the audit_log table with all the provided fields.

The ::jsonb cast tells PostgreSQL to store the dict as binary JSON — queryable and indexed.

conn=db_conn means this INSERT shares the same transaction as the parent operation. Commit or rollback together.

If the INSERT fails for any reason (constraint, disk full, etc.)...

...log the error to the application logs but do NOT raise it. The caller's code keeps running.

The Night Crew — Background Jobs

Some work is too slow to do during a user's request — like removing human DNA from a 5 GB sequencing file. JACKPOT runs these as scheduled background jobs, separate from the main API.

⏱️

Scrubber Queue

Runs every 60 seconds. Finds all samples with scrub_status = PENDING and submits them to the human-read removal pipeline. Updates status to IN_PROGRESS, then COMPLETE or FAILED.

🌙

Access Request Expiry

Runs every night at 2:00 AM. Finds pending dataset access requests that have exceeded their approval window and auto-denies them. Writes DENY_ACCESS_REQUEST to the audit log.

Why not Celery or Redis?

Many apps use Celery for background work. JACKPOT does not — it is explicitly listed in the architecture constraints as “no Celery, no Redis as task broker.” Simpler infrastructure for a platform that needs to be operated by public health agencies, not dedicated DevOps teams.

The single most common JACKPOT bug: wrong is_active column name

Organizations and Labs use active (no prefix). Everything else uses is_active. Mixing these up causes silent SQL errors where a soft-delete does not take effect or an active filter returns wrong results. Always check the schema when writing queries against orgs or labs.
