The Cast

Meet the 21 routers, one database, and the storage layer that holds it all together

Five Layers, One Platform

Think of JACKPOT like a hospital. The FastAPI server is the front desk. The routers are the individual departments. The database is the records room. Storage is the physical file archive.

⚡
FastAPI (main.py)

The entry point. Registers all 21 routers, wires up the CORS policy, starts the background scheduler, and serves the /health endpoint.

🗂️
21 Routers (backend/routers/)

Each router owns a domain: auth, ingest, samples, gisaid, users, organizations, and 15 more. Fully implemented: auth and gisaid. The rest are stubs returning {"status":"not implemented"}.

🗄️
PostgreSQL + SQLAlchemy (backend/database.py)

All 27 tables live here. SQLAlchemy manages the connection pool. Every query goes through execute_query() or execute_write() — routers never touch the database driver directly.

📦
MinIO / GCS (backend/storage.py)

Sequencing files are too large for a database. They live in an S3-compatible bucket. Locally that is MinIO (in Docker); in production it is Google Cloud Storage.

⏰
APScheduler / Cloud Scheduler (backend/jobs.py)

Background jobs run on a schedule: the scrubber queue every 60 seconds, and access-request expiry every night at 2 AM. Locally this uses APScheduler; in production it uses Google Cloud Scheduler.

Why this layout matters for steering AI

When you ask an AI coding agent to “add a new field to sample uploads,” you now know the exact files to mention: validator.py (add the field to the tier rules), routers/ingest.py (accept it in the payload), and schema/ (update the canonical schema). Vague instructions get vague results — specific file paths get precise changes.

The Database Helper That Powers Every Write

Every INSERT, UPDATE, and DELETE in JACKPOT goes through execute_write(). Here is the key part of it — with one pattern you will see everywhere.

CODE — backend/database.py 

def execute_write(
    query: str,
    params: dict | None = None,
    conn=None,
) -> list[dict]:
    if conn is not None:
        result = conn.execute(text(query), params or {})
        if result.returns_rows:
            cols = result.keys()
            return [dict(zip(cols, row)) for row in result.fetchall()]
        return []
PLAIN ENGLISH

Define a function that writes to the database. It takes a SQL string, optional parameters, and an optional database connection.

The SQL query to run — written as a plain string like "INSERT INTO orgs ..."

Values to substitute safely into the query — prevents SQL injection attacks.

An existing database session to join, so multiple writes share one transaction.

If a connection was passed in, use it (we are inside a bigger transaction)...

...run the query using that connection.

If the query returned rows (e.g., INSERT ... RETURNING *)...

...get the column names, then zip each row into a dictionary and return them all.

If nothing was returned (e.g., a DELETE with no RETURNING), return an empty list.

💡
RETURNING * — never SELECT after write

PostgreSQL lets you add RETURNING * to an INSERT or UPDATE to get the saved row back immediately. JACKPOT uses this everywhere instead of running a separate SELECT query. One round-trip instead of two — and you always get the database-generated values like auto-increment IDs and timestamps.
