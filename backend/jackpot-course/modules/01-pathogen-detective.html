The Pathogen Detective

What JACKPOT does — and the 8-step journey every pathogen sample takes

A Platform for Tracking Pathogens at the Source

Imagine a disease outbreak is spreading across Arizona. Health labs are collecting samples — nasal swabs, wastewater, livestock tissue — and sequencing the pathogen's genome to understand how it mutates and spreads.

The problem: every lab uses different file formats, different naming conventions, and different quality standards. Sharing data with global databases like GISAID or NCBI requires strict metadata standards. And every raw sequencing file contains traces of human DNA that must be scrubbed before any sharing.

🧬

Ingest Raw Data

Accept FASTQ and FASTA files plus structured metadata from public health labs.

✅

Validate Quality

Check metadata against a 3-tier quality standard — PRELIMINARY, ANALYZABLE, SUBMITTABLE — so only good data reaches global databases.

🔒

Scrub Human DNA

Remove human genetic material from every sample before it leaves the lab — a legal and ethical requirement for patient privacy.

🌍

Export to Global DBs

Generate GISAID-compatible CSVs and NCBI submission packages so Arizona data feeds global outbreak surveillance in real time.

What Happens When a Lab Uploads a Sample

Imagine a lab technician at the Arizona State Public Health Lab uploads a FASTQ file and fills out a metadata form. Here is every step JACKPOT takes in the next few seconds — in order.

1
File arrives at the API

The file and metadata hit one of 21 router endpoints on the FastAPI server.

2
Authentication check

Guards verify the user's JWT token and confirm they have permission to upload to the requested lab.

3
File type sniffed and paired

The file detector reads the first bytes to confirm the file is genuinely FASTQ (not mislabeled), then pairs R1 and R2 reads together.

4
PII scan

The DLP scanner checks all free-text fields for accidentally included personal information.

5
Metadata validated

The validator checks which quality tier the sample reaches — does it have enough fields to be just stored, analyzed, or submitted to global databases?

6
File staged to cloud storage

The raw file is uploaded to a staging bucket in MinIO (local) or GCS (production).

7
Record written to PostgreSQL

The sample row and an audit log entry are written to the database in the same transaction.

8
Scrubber job queued

A background job is scheduled to remove human DNA from the file. Until scrubbing completes, the sample's scrub_status stays PENDING.

The key insight: one request, many actors

A single upload triggers six different systems in sequence. If any step fails — bad metadata, missing permissions, storage error — the whole request is rejected cleanly and the database stays untouched. This is the beauty of ordered validation.

Your First Look at Real Code

Here is JACKPOT's health-check endpoint — the simplest piece of real code in the entire codebase. Read the plain English column to understand every line.

CODE 

@app.get("/health")
def health() -> dict:
    try:
        execute_query("SELECT 1")
        db_status = "connected"
    except Exception:
        db_status = "unavailable"
    return {"status": "ok",
            "version": __version__,
            "database": db_status}
PLAIN ENGLISH

Register this function at the URL path /health for GET requests.

Define a function called health that returns a dictionary (key-value pairs).

Try to run the following — if anything goes wrong, jump to "except".

Ping the database with the simplest possible query — just to see if it responds.

If that worked, mark the database as "connected".

If anything threw an error, catch it here...

...and mark the database as "unavailable" instead.

Send back a JSON response with the API status, its version number, and the database status.

🔍
The @app.get decorator

That @ symbol is called a decorator. It is the pattern FastAPI uses to connect a URL to a Python function. Every endpoint in JACKPOT starts with one.
