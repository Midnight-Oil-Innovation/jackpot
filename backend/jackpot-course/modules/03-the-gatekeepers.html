Logging In — The Hotel Keycard System

Think of JACKPOT's login system like a hotel. The front desk (Google OAuth) checks your ID and hands you a keycard (JWT). That keycard opens specific doors based on your role. When it expires, you get a new one from the front desk without re-checking your ID.

Why HTTP-only cookies, not localStorage?

JACKPOT sets JWT tokens as HttpOnly cookies, not in browser localStorage. This means JavaScript on the page cannot access the tokens — a stolen script cannot steal your session. The browser sends them automatically on every request.

How Every Request Gets Verified

Every protected endpoint calls get_current_user() first. Here is the real code from guards.py:

CODE — backend/auth/guards.py 

def get_current_user(request: Request) -> dict:
    settings = get_settings()
    if settings.env == "local":
        rows = execute_query(
            "SELECT * FROM users WHERE email = :e",
            {"e": settings.mock_user_email},
        )
        return rows[0] if rows else {"id": 1, ...}
    token = request.cookies.get("access")
    if not token:
        raise HTTPException(status_code=401, detail="Not authenticated.")
    payload = jwt.decode(token, settings.secret_key, ...)
    rows = execute_query("SELECT ... FROM users WHERE id = :uid", ...)
    return rows[0]
PLAIN ENGLISH

Define a function that takes an HTTP request and returns a user dictionary.

Load the app settings (database URL, secret key, etc.) from environment variables.

If we are running locally (not in production)...

...look up the mock user defined in docker-compose.yml by their email address...

(using a safe parameterized query so nobody can inject SQL)

...and return them as the logged-in user. This lets developers work without real Google login.

In production: read the “access” cookie from the request.

If there is no cookie, reject the request with HTTP 401 — Unauthorized.

Decode and verify the JWT using the app's secret key.

Look the user up in the database to confirm they still exist and are active.

Return the user's data — the router can now use it for permission checks.

Three Levels of Power

403 vs 401 — two very different errors

401 Unauthorized means “I don't know who you are — please log in.” 403 Forbidden means “I know exactly who you are, and you are not allowed to do this.” When you see a 403 in JACKPOT, look for a missing require_* guard call or an incorrect role assignment.
